\chapter{Global Architecture of the Proposed Digital Twin}
\label{chap:global_architecture}

\section{Introduction}

This chapter presents the global architecture of the Agrio Digital Twin smart irrigation platform. The architecture is designed as a cyber-physical loop: sense, transmit, store, synchronize, predict, simulate, recommend, validate, actuate, and record feedback. The chapter is organized into a small number of layers so that the physical prototype, communication, backend intelligence, deployment, and discussion remain readable.

\section{Architectural overview}

The architecture connects Libelium Smart Agriculture sensors, XBee radio-frequency communication, Raspberry Pi gateway processing, MQTT messaging, FastAPI backend services, PostgreSQL storage, a separated Random Forest ML service, Digital Twin state and simulation services, recommendation and scheduler services, a Next.js dashboard, a Flutter mobile application, a WeMos actuator, and a water pump. Figure~\ref{fig:6-1-global-overview-of-the-agrio-digital-twin-smart-irrigation-archite} gives the global view of this cyber-physical loop.

The global view should be read as a functional map rather than as a deployment diagram. Physical sensing creates field observations. The gateway prepares these observations for communication. The backend stores and processes the data. The Digital Twin maintains a synchronized virtual state. The ML and simulation layers support decision-making. The user validates or schedules actions. The actuator executes pump commands and sends feedback so the digital layer can reflect the physical result.

\section{Physical prototype and field layer}

The physical prototype and field layer groups the elements that are located near the plants or directly connected to irrigation equipment. It includes the controlled prototype environment, plants, irrigation line, water reservoir or supply, pump, relay wiring, Libelium Smart Agriculture sensing equipment, XBee radio communication, Raspberry Pi gateway, WeMos actuator, and pump feedback. This section intentionally avoids exact MQTT topic names; those details are concentrated in the MQTT communication layer.

The Libelium Smart Agriculture equipment collects soil and environmental measurements such as soil moisture, soil temperature, air temperature, relative humidity, rainfall, wind speed, wind direction, pressure, light intensity, or leaf wetness when the corresponding sensor is available. These measurements describe the current irrigation context and are needed for the Digital Twin state update.

XBee radio communication transfers sensing data from the field side to the Raspberry Pi gateway. The gateway acts as the edge bridge between field acquisition and the software platform. It receives data from the sensing equipment, prepares or standardizes the payload, and forwards it through the messaging infrastructure. This separation is useful because the sensing equipment, gateway, backend, and dashboard do not need to be physically colocated.

The WeMos actuator closes the physical-control side of the loop. It controls the relay connected to the pump and reports actuator state after commands. The pump and irrigation line represent prototype-scale actuation, not a commercial irrigation network. Feedback from the actuator is important because the system must know whether a requested physical action was reflected by the device.

\section{MQTT communication layer}

The MQTT communication layer exchanges asynchronous messages between the physical prototype and the software platform. MQTT follows a publish/subscribe model: producers publish messages to topics, the broker routes these messages, and subscribers consume the topics they need. This decouples the Raspberry Pi gateway, backend services, WeMos actuator, and dashboard-related services.

In Agrio, MQTT supports three main flows. The first flow is sensor data acquisition from the gateway to the backend. The second flow is actuator command publication from the backend to the WeMos actuator. The third flow is actuator feedback from the WeMos actuator back to the backend and dashboard. Figure~\ref{fig:mqtt_communication_architecture} presents this communication view.

\section{Backend, data, Digital Twin, and intelligence layers}

The backend, data, Digital Twin, and intelligence layers form the software core of the platform. The FastAPI backend exposes REST endpoints to the web dashboard and mobile application, receives MQTT-originated data, validates and normalizes payloads, maps devices to zones, persists records, updates the Digital Twin state, calls the ML service, runs simulation, generates recommendations, handles validation, manages schedules, and publishes actuator commands when an action is required.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{figures/chapter_06/figure_6_4_backend_architecture_clean.png}
    \caption{Internal backend architecture of the FastAPI-based Digital Twin platform.}
    \label{fig:backend_architecture}
\end{figure}

The data layer is based on PostgreSQL. It stores agricultural entities, sensor readings, weather records, forecasts, device health logs, Digital Twin states, state history, prediction results, simulation scenarios and outputs, recommendations, irrigation events, control commands, and execution feedback. This persistence model supports traceability from measurement to decision and from decision to physical feedback.

The Digital Twin layer maintains the virtual representation of the monitored irrigation zone. It updates the current state from recent sensor readings, weather records, previous state values, actuator feedback, and prediction outputs. State history is preserved so the system can analyze evolution rather than only the latest measurement.

The ML service is separated from the backend. It loads Random Forest models and returns irrigation need, suggested hour, confidence values, and a recommended action. The backend stores the result and can use fallback logic when inference is unavailable. The simulation and recommendation services then combine the Digital Twin state, ML output, forecast context, and rules to support an interpretable decision. Human validation remains part of the workflow before supervised physical execution.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{figures/chapter_06/figure_6_5_digital_twin_processing_clean.png}
    \caption{Digital Twin processing workflow from live measurements to prediction, simulation, and supervised irrigation action.}
    \label{fig:digital_twin_processing_workflow}

Figure~\ref{fig:digital_twin_processing_workflow} explains the runtime logic of the intelligent layer. Live data are ingested and stored. The current zone state is updated. The backend prepares a feature payload for the ML service. Prediction results are stored. Simulation compares possible actions. The recommendation layer creates a decision that can be validated, scheduled, or kept for monitoring. When the user validates an action or a schedule becomes due, the backend uses the device-control workflow to publish the actuator command and record feedback.

\section{Deployment architecture}

The deployment architecture is defined with Docker Compose in order to run the prototype as a reproducible multi-service platform. The objective is not to claim production-grade cloud deployment, but to coordinate the services required for demonstration and technical validation: backend API, PostgreSQL database, ML service, frontend, scheduler, MQTT broker, and optional ngrok access for prototype/mobile testing.

\section{Discussion}

The architecture is modular and extensible. The physical layer is separated from the MQTT layer, the backend is separated from the ML service, and persistence is centralized in PostgreSQL. This organization supports the Digital Twin loop without presenting unsupported services as implemented. The main limitations are controlled-environment validation, limited security hardening, and the absence of multi-season field data.

\section{Conclusion}

This chapter presented the proposed Digital Twin architecture through compact layers: architectural overview, physical prototype and field layer, MQTT communication layer, backend/data/Digital Twin/intelligence layers, and deployment architecture. The architecture forms a traceable cyber-physical irrigation loop rather than an isolated dashboard or standalone prediction model. The following chapter details how this architecture is implemented in the backend, database, and IoT ingestion pipeline.
