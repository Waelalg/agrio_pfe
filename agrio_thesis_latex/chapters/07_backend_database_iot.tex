\chapter{Backend, Database, and IoT Data Ingestion}

\section{Introduction}

This chapter describes the implementation of the backend, database, and IoT ingestion pipeline. It explains how MQTT messages become database records, Digital Twin states, ML predictions, and dashboard updates.

\section{FastAPI backend organization}

The backend is implemented with FastAPI. It exposes REST endpoints under the /api/v1 prefix, provides automatic OpenAPI documentation, configures CORS for frontend/mobile access, initializes services, and starts the MQTT subscriber when the system is configured for MQTT data source mode.

\section{API modules}

The API is organized around users, farms, plots, soil profiles, crops, zones, sensors, weather records, irrigation events, Digital Twins, predictions, recommendations, control commands, simulations, dashboard aggregation, device control, ML proxy, forecasting, system status, and debugging. This organization reflects the functional separation of the platform.

\section{MQTT payload structure}

MQTT communication in Agrio is organized around three payload families. The first family contains sensor-ingestion messages published on the \texttt{sensors/data} topic. These messages transport soil, weather, and environmental measurements from the physical prototype to the backend. The second family contains WeMos status feedback published on the \texttt{smart\_irrigation/wemos1/status} topic. These messages allow the backend and dashboard to know the current state of the actuator pins. The third family contains actuator commands sent to the \texttt{smart\_irrigation/wemos1/cmd} topic. These commands are generated by the backend after a manual action, validated recommendation, or scheduled irrigation event.

Instead of presenting all payloads in one overloaded visual, the payload structure is decomposed into three focused views. The first view describes the sensor-ingestion payload, the second view describes actuator status feedback, and the third view explains the command payload and valid command values.

The sensor-ingestion payload represents the physical-to-digital data flow. A Libelium/Raspberry Pi gateway or MQTT test publisher sends measurements to the \texttt{sensors/data} topic. The backend consumes this message, validates the JSON structure, normalizes field names and units, resolves the target management zone, and stores the resulting measurements. The most important fields are \texttt{device\_id}, \texttt{zone\_id}, \texttt{soil\_moisture}, environmental variables, wind information, and \texttt{timestamp}. Soil moisture may be received as a fraction or percentage and is normalized before being used by the Digital Twin and ML service.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{figures/chapter_07/7.1.2_wemos_status_payload_cropped.png}
    \caption{MQTT and REST payloads used in the Agrio platform: WeMos status feedback payload.}
    \label{fig:mqtt_payload_wemos_status}
\end{figure}

The WeMos status feedback payload represents the physical-to-digital actuator feedback flow. The WeMos publishes its current pin states to \texttt{smart\_irrigation/}\linebreak[1]\texttt{wemos1/status}. In the prototype, \texttt{D5} represents the pump-control output and \texttt{D3} can represent a lamp or indicator output. This feedback is important because the software platform must know whether the actuator state changed after a command. It supports dashboard visualization, command traceability, and synchronization between the physical actuator and the Digital Twin layer.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{figures/chapter_07/7.1.3_actuator_command_payload_cropped.png}
    \caption{MQTT and REST payloads used in the Agrio platform: actuator command payload and command values.}
    \label{fig:mqtt_payload_actuator_command}
\end{figure}

The actuator command payload represents the digital-to-physical control flow. The dashboard, mobile application, scheduler, or validation workflow sends a REST request to the backend. The backend validates the requested action and publishes a plain-text command to \texttt{smart\_irrigation/wemos1/cmd}. The command payload is intentionally simple because it is consumed by a low-power WeMos controller. Valid command values include \texttt{ON\_D5}, \texttt{OFF\_D5}, \texttt{ON\_D3}, \texttt{OFF\_D3}, \texttt{ALL\_ON}, and \texttt{ALL\_OFF}.

\section{Parser and normalization}

The parser is applied mainly to sensor-ingestion payloads received from the MQTT topic described in Table~\ref{tab:mqtt_topics}. Its role is to transform an incoming payload into a validated internal representation that can be stored, reused by the Digital Twin, and converted into ML features. The parser first checks that the payload is valid JSON. It then verifies required fields such as device identifier, zone identifier when available, timestamp, and at least one useful measurement. Payloads that cannot be parsed or do not contain enough information are ignored or marked as errors instead of being inserted as misleading records.

Normalization makes heterogeneous payloads usable by the rest of the system. Field aliases are mapped to canonical names so that equivalent names for soil moisture, temperature, humidity, rainfall, wind, or light can be interpreted consistently. Timestamps are parsed into a common datetime format. Soil moisture values are normalized so that fractions such as \texttt{0.42} and percentages such as \texttt{42} can be compared in the same scale. Numeric strings are converted into numerical values when possible. Light-intensity values with suffixes are converted to lux-style values. Wind-direction labels such as north, north-east, or compass abbreviations are converted into degrees when numerical features are required.

Missing values are handled explicitly. A missing optional field does not necessarily invalidate the whole payload; it can be stored as unavailable and later represented by missing-value flags in the ML feature payload. This behavior is important because field sensors may not all report at the same time. The parser therefore produces a validation result: accepted, accepted with missing optional values, ignored, or error. This result protects the real-time pipeline and keeps ML feature preparation consistent with the dataset adaptation logic described in the Digital Twin and ML chapter.

\section{Device mapping and persistence}

After parsing, the backend resolves the \texttt{device\_id} and the corresponding \texttt{zone\_id}. If the payload already contains a valid zone identifier, it is used directly after validation. If the payload identifies only the physical device, the backend uses configured sensor or device mappings to find the management zone. When allowed by the implementation workflow, missing mappings can be created or completed for known prototype devices; otherwise the payload is rejected or stored only as an unmapped diagnostic record.

Persistence separates measurement types according to their role in the domain model. Sensor measurements are stored as \texttt{sensor\_readings}, while environmental snapshots such as air temperature, humidity, rainfall, wind, and pressure are stored as \texttt{weather\_records} when available. Sensor metadata and mappings make it possible to connect a physical sensor type to the table records it produces. Device status information is also maintained so the dashboard can show freshness, last-seen time, and actuator state.

The same persistence principle is used for control traceability. Recommendations, validated decisions, irrigation events, control commands, and execution feedback are stored as related records. This means that a physical pump action can be traced back to a recommendation or schedule and forward to the actuator feedback. Database writes should be treated as a consistent unit where possible: a parsed payload should not update the Digital Twin state without preserving the measurements that produced that state. This consistency supports Digital Twin synchronization and later validation.

\section{Real-time pipeline}

The real-time pipeline is triggered after successful MQTT ingestion and persistence. It loads the latest sensor and weather records for the zone, evaluates freshness and device health, updates the current Digital Twin zone state, prepares an ML feature payload, calls the ML service, stores prediction results, appends a \texttt{zone\_state\_history} record, and updates recommendations. This pipeline converts raw measurements into actionable Digital Twin data.

\begin{enumerate}
\item Load latest sensor and weather records for the resolved management zone.
\item Evaluate freshness and health based on last-seen timestamps and available status records.
\item Update the current zone state from recent measurements and previous state values.
\item Build the ML payload and call the Random Forest inference service.
\item Store the prediction result, including confidence and fallback status when applicable.
\item Append a zone-state-history record to preserve temporal evolution.
\item Generate or update the irrigation recommendation from state, prediction, simulation context, forecast context, and rules.
\item Expose the updated state to dashboard and mobile clients through API responses.
\end{enumerate}

If the ML service is unavailable, the pipeline can use fallback logic rather than stopping the entire workflow. The fallback output is stored as such so that later interpretation does not confuse it with a normal model prediction. The scheduler and control workflow consume the resulting state and recommendations only after validation or scheduling rules require action.

\section{PostgreSQL schema}

The PostgreSQL schema contains tables for users, farms, plots, zones, soil profiles, crops, irrigation networks, sensors, readings, weather records, device health, forecasts, digital twins, zone states, predictions, simulations, recommendations, alerts, commands, events, and feedback. This structure supports traceability from sensor data to action.

\section{Error handling and fallback}

If payload validation fails, the ingestion is marked as ignored or error. If the ML service is unavailable, the system can build a fallback rule-based prediction and store a fallback twin state. This prevents complete workflow failure when the ML service is temporarily unavailable.

\section{Conclusion}

This chapter described the backend, database, and IoT ingestion mechanisms that transform MQTT-originated field messages into structured records. It clarified the role of payload parsing, normalization, device mapping, persistence, runtime sequencing, and actuator feedback. These mechanisms provide the operational foundation required by the Digital Twin and machine-learning layer presented in the next chapter.
