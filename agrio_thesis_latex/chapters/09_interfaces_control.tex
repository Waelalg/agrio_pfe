\chapter{User Interfaces and Irrigation Control}
\label{chap:interfaces_control}

\section{Introduction}

The user interface is the operational face of the Digital Twin. It transforms sensor data, ML outputs, MAS decisions, simulation results, recommendations, schedules, and actuator status into understandable information. Agrio includes a Next.js web dashboard and a Flutter mobile application.

\section{Frontend architecture}

The frontend is organized into pages for dashboard, forecast, Digital Twin simulation, schedules, validated decisions, zone details, and the MAS decision panel. It communicates with the backend and decision services through REST APIs using a configured API base URL and periodically refreshes dashboard data.

\section{MAS decision interface}

The MAS decision interface is planned as the frontend point where the operator can request and inspect the explainable multi-agent irrigation decision. The page or panel should explain what the MAS is, show the input fields sent to the service, and make clear that the service supports decision-making rather than replacing human validation. The expected inputs include device identifier, location, plant type, optional zone, target moisture range, irrigation duration, and a farmer note describing visible plant or soil observations.

The response view should display the final decision, confidence, risk level, suggested hour, recommended duration, farmer-friendly explanation, evidence cards, and warnings. The evidence cards should separate Digital Twin state, ML prediction, weather context, agronomy, water balance, and safety rules so that the user can understand why the MAS returns \texttt{KEEP\_OFF}, \texttt{START\_IRRIGATION}, or \texttt{SCHEDULE\_IRRIGATION}. The interface must not present the MAS as a computer-vision system, because the implemented workflow relies on structured field context and farmer text notes.

\section{Mobile application}

The Flutter mobile application provides a portable access point to the Agrio Digital Twin platform. It allows the user to monitor the irrigation zone, inspect sensor and Digital Twin information, follow recommendations, and access decision-support functions from a smartphone. This is important because irrigation decisions are often made outside a desktop environment.

\subsection{Mobile access and navigation}

The mobile access screen connects the smartphone interface to the deployed backend service. It contains the server address, user credentials, and the entry button used to open the mobile workspace. This screen supports the Digital Twin workflow by allowing the operator to reach the monitoring and decision-support services from the field during prototype testing.

Overall, the mobile application extends the Digital Twin workflow beyond the web dashboard by giving the operator portable access to monitoring, decision support, scheduling, and supervised irrigation control. However, the mobile application remains a prototype interface. A production deployment would require stronger authentication, HTTPS configuration, role-based access control, and usability testing with farmers.



\section{Conclusion}

The interface layer makes the Digital Twin usable by translating backend records, ML outputs, MAS decisions, simulations, recommendations, schedules, and actuator status into operational screens. The web dashboard and mobile application support monitoring, forecasting, scenario exploration, explainable decisions, validated decisions, schedule management, and manual pump control. This layer is therefore not only a display component; it is the human-in-the-loop point where the user can inspect the Digital Twin state and decide whether an irrigation action should be executed.
