\chapter{Results, Validation, and Discussion}

\section{11.1 Introduction}

Validation in this thesis focuses on technical correctness of the prototype workflow. The objective is to demonstrate that data can move from physical sensors to MQTT, database, Digital Twin state, ML prediction, dashboard, simulation, recommendation, and pump command.

\section{11.2 Prototype validation context}

The system was tested on a controlled experimental prototype, not on a commercial farm. Therefore, validation proves functional integration and workflow feasibility. Agronomic water-saving claims require future field experiments.

\section{11.3 Sensor data acquisition}

The HiveMQ screenshot shows sensor data published on sensors/data and WeMos status published on smart\_irrigation/wemos1/status. This proves that the communication layer receives physical and actuator information.

\section{11.4 Database persistence}

The database screenshot shows stored sensor readings with id, zone\_id, sensor\_type, value, quality\_flag, source, and timestamp. This proves that MQTT-originated measurements are persisted in PostgreSQL.

\section{11.5 Dashboard synchronization}

The dashboard shows the latest moisture, zone state, sensor health, twin status, environment snapshot, and recommendation. This proves that backend data is exposed to the user interface.

\section{11.6 ML prediction validation}

The ML service should be validated through /health, /metadata, and /predict screenshots. These show that models are loaded, metadata is available, and prediction output contains irrigation need, suggested hour, confidence, and recommended action.

\section{11.7 Simulation validation}

The Digital Twin simulation result compares no-irrigation, with-irrigation, and ML-selected paths. This proves that the platform can run what-if analysis rather than only display current values.

\section{11.8 Pump control validation}

Pump control is validated through MQTT command evidence and WeMos status feedback. The key expected sequence is ON\_D5 command, D5 ON status, OFF\_D5 command, and D5 OFF status.

\section{11.9 Discussion of results}

The results demonstrate end-to-end integration. The project succeeds in implementing the core Digital Twin loop in a controlled environment. The main limitation is that the loop has not yet been validated across seasons, crops, and real field variability.

\section{11.10 Comparison with literature}

Compared with MQTT smart irrigation systems, Agrio adds Digital Twin state and simulation. Compared with ML-only irrigation systems, Agrio integrates prediction into a deployed backend and dashboard. Compared with field-validated DT systems, Agrio is less agronomically validated but more transparent as a student engineering prototype.

\section{11.11 Limitations}

Limitations include controlled prototype scale, limited long-term data, dataset adaptation constraints, lack of satellite/UAV integration, limited security hardening, and the need for sensor calibration. These are normal for a final-year prototype but must be addressed before real deployment.

\section{11.12 Future work}

Future work includes field deployment, multiple zones, crop-specific calibration, satellite/UAV data assimilation, improved evapotranspiration modeling, model retraining, reinforcement learning optimization, emergency stop mechanisms, cybersecurity, and farmer usability studies.

\section{11.13 Conclusion}

This chapter validated the main technical workflow and discussed limitations. The system demonstrates a strong proof of concept for a Digital Twin-based intelligent irrigation platform.
